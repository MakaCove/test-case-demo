# Test Case Rules

## 文档语言（用例）

遵循 `05_OUTPUT_AND_REPORTING.md`「文档语言」总则。核心：用例 Markdown/JSON 中面向人读字段使用**简体中文**；`title` 为简短中文标题；`type` 使用中文枚举；`assertions` 写中文可执行判据。

---

## 用例结构模板（每条）

| 字段 | 类型 | 说明 |
|------|------|------|
| `caseId` | string | 格式 `TC-<模块缩写>-<三位序号>`，如 `TC-AUTH-001` |
| `title` | string | 简短中文标题 |
| `endpointKey` | string | `METHOD /完整路径` |
| `priority` | enum | P0/P1/P2/P3 |
| `type` | enum | 功能/异常/边界/安全/性能 |
| `preconditions` | string | 中文描述，前置数据/环境要求（含登录态要求） |
| `request` | object | 包含 method/url/pathParams/headers/query/body |
| `assertions` | array | 中文可执行判据列表 |
| `expectedResult` | string | 中文描述期望结果 |
| `cleanup` | string | 中文描述数据清理方式；若无则填"无"，不得留空 |
| `tags` | array | 如 `["鉴权", "P0", "注册"]` |
| `sourceEvidence` | string | 格式：`<相对路径>#<类名或方法名>` |
| `status` | enum | ready / draft / blocked |
| `blockedReason` | string | 仅 `blocked` 用例必填，说明阻断原因与建议解除条件 |

---

## 用例状态规则

- **ready**：字段完整、依赖环境可用，可直接生成测试代码。
- **draft**：结构完整但存在不确定因素（如测试数据尚未确认、接口文档不清晰）；进入 Step 6 后生成带 `@Disabled` 的骨架方法，不跳过。
- **blocked**：依赖外部服务、需要特殊权限、环境未就绪等情况；必须填写 `blockedReason`，不生成代码，在回传中单独列出。

---

## 核心设计原则

1. **可重复**：任意顺序单独运行均能通过，不依赖全局状态
2. **独立性**：不依赖其他用例的执行结果；每条用例自建、自清数据
3. **可读性**：不看代码就能理解用例意图
4. **完整性**：覆盖正常/异常/边界三类场景
5. **可追溯**：每条用例通过 `caseId` + `sourceEvidence` 可追溯到来源代码
6. **顺序无关**：禁止依赖测试方法执行顺序；若接口存在固有业务顺序（如"先创建再查询"），应在**同一个测试方法内**完成，而非分拆为多个相互依赖的 `@Test`

## 按接口语义的最小用例集合

### 查询类（GET list/detail）
- 正常查询（返回数据，验证关键字段）
- 资源不存在（返回 404 或空列表）
- 分页默认值（未传分页参数时的默认行为，验证 `total`/`pageSize`/`list` 结构）
- 必填参数缺失（返回 400）
- 路径参数非法（`/users/abc` 当 id 为整型时，返回 400 或 404）
- 未登录（受保护接口返回 401）

### 创建类（POST create）
- 成功创建（返回新建资源，验证 id 非空、写后读一致）
- 必填字段缺失（返回 400，错误信息指向对应字段）
- 字段类型/格式错误（返回 400）
- 字段边界值（最大长度、最小值、特殊字符，见"参数边界值规则"）
- 唯一键冲突（返回 409 或业务错误码）
- 未登录（返回 401）

### 更新类（PUT/PATCH）
- 全量更新成功（验证所有字段均已变更）
- 部分字段更新成功（PATCH，验证未传字段保持原值）
- 资源不存在（返回 404）
- 只读字段尝试更新（忽略或返回 400，视业务约定）
- 未登录（返回 401）

### 删除类（DELETE）
- 正常删除（验证删后查询返回 404 或空）
- 重复删除幂等性（返回 404 或成功，视业务约定）
- 资源不存在（返回 404）
- 未登录/无权限（返回 401/403）

### 批量类（batch）
- 全部成功（验证每项均返回成功标记）
- 部分成功（验证返回成功/失败明细，失败项有原因）
- 空输入（返回 400 或空结果，视业务约定）
- 超上限（返回 400 或 413，错误信息含上限值）

### 异步类（submit/status/cancel）
- 提交成功（返回任务 ID，验证 ID 格式）
- 状态流转（提交→执行中→完成，可用轮询或固定等待验证）
- 取消路径（已提交状态可取消，已完成不可取消）
- 重复提交幂等（返回已有任务 ID 或 409）

### 导入导出类（upload/export）
- 正确格式文件上传成功（验证返回的文件 ID 或记录数）
- 错误格式文件拒绝（返回 400，错误信息含格式说明）
- 空文件拒绝（返回 400）
- 超大文件拒绝（返回 413 或 400，视业务约定）
- 导出结果结构合法（字段完整、格式正确、非空）

## 横切维度（每类接口均需考虑）

| 维度 | 说明 | 最少覆盖 |
|------|------|---------|
| 鉴权与权限 | 无/非法 token→401，无权限→403 | 每个受保护接口必须覆盖 |
| DTO 字段校验 | 必填/类型/长度/格式边界 | 每个有 `@Valid` 的入参必须覆盖缺失与格式错误 |
| 路径参数合法性 | `/users/{id}` 的 id 非法类型、负数、超长 | 有路径参数的接口必须覆盖 |
| 数据一致性 | 写操作后通过读接口验证（写后读） | 写类接口主流程必须覆盖 |
| 服务规则 | 状态流转是否合法（如"已完成"不可再取消） | 有状态机的接口必须覆盖 |
| 列表/分页结构 | `total`/`pageSize`/`list` 字段存在且语义正确 | 返回列表的接口必须覆盖 |
| 外部依赖异常 | 超时/空数据/降级（若有 Mock 能力则覆盖） | 可选，有 Mock 环境时覆盖 |

## 参数边界值规则（新增，必须遵守）

生成用例时，**对每个有 `@Size`、`@Min`、`@Max`、`@NotBlank`、`@Length` 等校验注解的字段**，必须覆盖以下边界：

| 边界类型 | 说明 | 用例 type |
|---------|------|----------|
| 空字符串（`""`） | 与 null 不同，需单独覆盖 | 异常 |
| null | 缺失字段（JSON 中不传该 key） | 异常 |
| 最小合法值 | 如 `@Min(1)` 时传 1 | 边界 |
| 最大合法值 | 如 `@Size(max=100)` 时传 100 个字符 | 边界 |
| 超出最大值 | 如传 101 个字符 | 异常 |
| 特殊字符 | `<script>`, `'`, `"`, `\n`, 中文、Emoji | 边界/安全 |
| 负数/零 | 数值型 `@Min(1)` 时传 0 或 -1 | 边界 |

**路径参数边界**（`/users/{id}`）：
- 合法格式（如正整数）：主流程覆盖
- 非整数格式（如字母、小数）：返回 400 或 404
- 超大数值（如 `Long.MAX_VALUE` + 1）：返回 404 或 400

## 登录态与 Token 前置规则（新增，必须遵守）

### 测试类级别

- 每个 `*ApiTest` 类须在类注释中声明**鉴权策略**（"本类所有接口均受 JWT 保护"或"部分接口开放"）。
- 需要 token 的测试类，**必须在 `@BeforeAll` 或 `@BeforeEach` 中统一获取 token**，禁止在每个测试方法内分别登录。
- token 获取逻辑封装到 `apitest/support/` 中的工具类（如 `TokenHelper`），禁止在 `*ApiTest` 中重复实现。

### Token 缓存策略

- `@BeforeAll`（类级别，推荐）：整个测试类共享一个 token，适用于 token 有效期远大于测试类执行时间的场景。
- `@BeforeEach`（方法级别）：每个方法单独获取 token，适用于需要验证 token 刷新/过期的场景，或测试类执行时间较长时。
- 若 token 可能在测试执行中过期，须在 `TokenHelper` 中加入过期检测与自动刷新逻辑。

### 鉴权失败用例

- 鉴权失败用例（无 token / 非法 token / 过期 token）不使用 `TokenHelper`，直接在方法内手动构造无效 token 或不携带 Authorization 头。
- 禁止复用同一个"有效 token"来测试 401 场景（会干扰结论）。

## 测试数据规则

1. 每条用例自行准备数据，避免用例间耦合
2. `cleanup` 字段不得留空；产生的数据**必须**在 `@AfterEach` 或方法末尾清理
3. **cleanup 失败不影响断言结果**：清理逻辑须用 `try-finally` 包裹，确保 cleanup 异常不会掩盖测试本身的 pass/fail 结论
4. 唯一值使用时间戳 + 随机数生成（如 `"test_user_" + System.currentTimeMillis()`）
5. 测试专用数据前缀约定（如 `[TEST]` 或 `test_`），便于手动或自动批量清理
6. 敏感数据（密码/token/密钥）不硬编码，从 `application-test.yml` 或环境变量读取
7. 若用例依赖特定的前置数据（如"已存在的用户"），须在 `preconditions` 中说明，并在 `@BeforeEach` 中通过接口创建而非假设数据库已有

---

## 测试顺序与独立性规则（新增，必须遵守）

1. **禁止**使用 `@TestMethodOrder(OrderAnnotation.class)` 让多个 `@Test` 方法相互依赖执行顺序。
2. 若接口有固有业务顺序（如"创建 → 更新 → 删除"验证完整流程），应在**同一个测试方法内**串联调用，不拆分为多个 `@Test`。
3. `@BeforeAll` 只放**类级别的一次性准备**（如获取 token、建立连接），不放具体测试数据的创建（测试数据放 `@BeforeEach`）。
4. `@AfterEach` 负责清理**本次测试方法产生的数据**；`@AfterAll` 负责清理**类级别共享资源**（如 token 缓存）。

---

## 优先级建议

| 级别 | 含义 | 典型场景 |
|------|------|---------|
| P0 | 核心主流程，失败阻塞发布 | 登录、核心增删改查成功路径 |
| P1 | 关键异常与边界，失败影响质量 | 401/403、必填校验、唯一冲突、边界值 |
| P2 | 普通场景，不影响核心流程 | 分页默认值、部分字段更新、路径参数非法 |
| P3 | 极端/性能/兼容 | 超大数据量、并发幂等、特殊字符 |

---

## 代码注释规则（生成测试代码时强制）

1. 每个测试类必须有类注释，说明覆盖的 endpoint 范围、鉴权策略、数据准备策略。
2. 每个测试方法必须有多行注释，至少包含：`caseId`、`endpointKey`、`title`、`preconditions`、`assertions`、`sourceEvidence`。
3. 请求体构造、鉴权处理、断言聚合、数据清理等关键代码块必须有"意图型注释"（解释原因/约束），禁止仅复述代码字面动作。
4. 用例文档（`api-test-cases-*.json`）变更后，测试方法注释必须同步更新，保证可追溯一致性。

---

## Allure Step 标题规则（生成测试代码时强制）

1. 每个测试方法至少有一条主 `Allure.step`，用于说明该用例"在验证什么"。
2. 主 step 标题必须包含：`caseId` + `endpointKey` + 中文"用例目的/预期"。
3. 推荐格式：`caseId=<…> | endpointKey=<METHOD path> | 目的=<中文描述>`。
4. 禁止只写技术性标题（如方法名、`send request`、`assert response`），必须让测试报告读者不用看代码就能理解用例意图。
5. 单条用例内含多次 HTTP 请求时，必须加嵌套中文子 step，禁止内层全是匿名 HTTP。
